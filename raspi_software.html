OBD2 運行データ連携 実装済み

車両: ハイエース TRH219W（ワゴン・4WD・ガソリン、VIN TRH219-0054064で確定）。
OBD2ポートに接続したBLEアダプタ「OBDBLE」（MAC: BC:9A:78:14:A6:50）を、haiace-monitor/readers/obd_reader.pyからbleakライブラリでGATT直接接続して読み取る。Classic Bluetooth（SPP/rfcomm）ではなくBLE方式（サービス0000fff0配下、fff2=write / fff1=notify にATコマンドをUART透過で送受信）。

PID内容状態備考
01A6オドメーター（総走行距離）対応「満タンにした」ボタンの給油記録に使用。実機確認済み
010Cエンジン回転数対応エンジン始動判定に使用（下記参照）
015E瞬間燃料消費率(L/h)対応燃費ロガー統合の候補、未統合
0902VIN（車台番号）対応TRH219-0054064取得済み
0131DTCクリア後走行距離対応3040km時点で取得、01A6との整合性確認済み
012F燃料残量(%)非対応本車両のECUは非公開。obd/fuel_range_check.pyは現状動作しない
015Cエンジン油温非対応
0105 / 010D / 0146 / 0142水温・速度・外気温・電圧対応ATSP0直後の初回クエリでプロトコル自動検出が不安定になる既知の問題（ELM327共通）。本番PIDの前にダミーの0100クエリを送るウォームアップを追加して解決。実機確認済み(2026-09-17、水温72℃・速度0km/h・外気温27℃・電圧13.862V)。collector.pyには一度きりの検証用関数として統合済みだが、常時ポーリングへの本格統合は未着手
給油記録機能（2026-09-17に自動化）: 給油直後はエンジンが止まっておりOBD2が応答しないため、「満タンにした」を押した時点(POST /api/fillup)ではfillup_pending.jsonに「記録待ち」フラグを立てるだけにし、実際の読み取りはcollector.pyが走行充電器(Orion)の通電を検知した時点(=エンジン再始動時)に自動でread_odometer()を実行してfillup_state.jsonに保存する設計に変更。ユーザーは給油後にボタンを押すだけで、エンジン再始動時の追加操作は不要。ダッシュボードには「記録待ち(エンジン始動待ち)」バッジで進行状況を表示。実機確認済み（2026-09-17、3248.4km）。
未着手: 平均燃費の実測値確定と、（現在の01A6 − 給油時01A6）÷平均燃費 による残燃料・走行可能距離の計算処理。設計方針（距離ベース方式、015E時間積分方式より運用が楽）は合意済み。

エンジン始動自動検知 実装済み（方式変更）

当初はOBD2 BLEアダプタの接続挙動（下記の判定アルゴリズム）で判定する設計だったが、2026-09-17により単純で既に安定しているOrion走行充電器のBLEポーリングで代替する方式に変更・実装した。collector.pyのOrion読み取りでoutput_voltage * output_current > 1.0Wを検知した瞬間を「エンジン始動」とみなす（is_charging_now）。既存の30秒ポーリングに相乗りするだけで新規のGATT接続ループが不要になり、給油記録の自動化（上記）とOBD2 PID再検証診断（上記）の両方のトリガーとして実機で使用中。

下記のOBD2接続挙動ベースの判定アルゴリズムは、当初の設計として合意はしたが、Orion方式の方が単純・低コストで確実だったため未実装のまま採用を見送った。将来Orionを撤去する等でこの前提が崩れた場合の代替案として記録を残す。
状態GATT接続PIDクエリ(010C等)応答
エンジンOFF確立直後(~0.3秒)に必ず切断-
ACC不安定（2回中1回失敗の実績あり）完全無応答（NO DATAすら返らない）
エンジンON安定正常応答
判定アルゴリズム（合意済み）:
① ラズパイが定期的（例: 30秒毎）にBLE GATT接続を試みる
② 接続が確立し即座に切断されず安定した場合、直後に010Cを問い合わせる
③ 有効な回転数が返れば → エンジン始動と確定
④ 接続不安定 / 010CがNO DATA → ACC状態または未始動と判定
接続成功だけでは判定不可: アダプタは常時アドバタイズしており「接続可能になった」を受動的に検知する仕組みがない。またACC状態でもGATT接続自体は成功することがあるため、接続成功のみをフラグにすると誤検知する。PID応答の有無まで含めて初めて確実な判定になる。
このGATT+PID方式は結局実装しなかった（上記の通りOrion方式に置き換え）。

車内Androidタブレット連携 現在地・天気・観光 実装済み 音声操作 設計中

車内に常設するAndroidタブレット（T90・Android 16・Wi-Fi専用・root化なし）をラズパイと連携。2026-10-10 に現在地連携を実装・実機確認。

① 現在地 → 天気・観光情報 実装済み 2026-10-10

要素内容
タブレット側Termux（F-Droid版）+ Termux:API + Termux:Boot。~/haiace-gps.sh が5分おきに termux-location の結果を POST /api/location へ送信。送信先はルーターLAN（192.168.0.198）→ Tailscale（100.99.198.121）の順
ラズパイ側travel_info.py（新規）。location_state.json に保存・location_log.jsonl に追記。天気=Open-Meteo（現在＋12時間予報）、地名=Nominatim、観光地=Overpass（半径10km・最大30件：温泉・道の駅・展望・博物館・城・Wikipedia記事のある寺社/山/滝）。すべて無料・キー不要
通信量対策結果を travel_cache.json に保存し、天気=5km移動/30分、地名=1km/1日、観光地=3km/1日 でのみ再取得。失敗後は10分空ける
表示ダッシュボードに「現在地」カード（GET /api/travel-info）。観光地はGoogleマップ／Wikipediaへリンク
タブレットにGPSが無い: GPSTestで衛星0個（窓際）。Wi-Fi専用機のため非搭載と判断。現在はWi-Fi電波による位置推定（誤差100m程度）で、山間部では取れない見込み。対策候補：① Pi5にUSB GPS（2,000円前後・最も確実） ② モバイルルーターの基地局情報から推定（取得可否は未調査）。
導入でつまずいた点:
・Play Store版TermuxはTermux:API非対応 → F-Droid版で入れ直し
・入れ直し直後は apt update && apt full-upgrade が必要（curlがopensslと不整合で起動しない）
・Termux:APIの位置権限が「使用時のみ」だと画面オフで取得失敗 → 「常に許可」で解決
・再起動後にTailscaleが繋がらない → Androidの設定でTailscaleを「常時接続VPN」に
・公開Overpassサーバーは不安定（around: は30秒タイムアウト、公式は504）→ bbox指定＋3サーバー切替

② タブレットの保守（Macから操作）

当初案のADBではなく、Termuxのsshd（ポート8022・Macの鍵のみ）をTailscale越しに使う方式にした。ssh -p 8022 100.86.179.4（Tailscale名 t90）。Termux:Bootで起動時にsshdと送信スクリプトを自動起動（再起動テスト済み）。端末の再起動はroot権限が無いためMacからは不可。

③ タブレットのセンサー（実機調査）

ありなし
加速度センサー（傾き・揺れ・動き検知）・前後カメラ・マイク・スピーカー・Wi-FiGPS・照度・気圧・磁気（方位）・温度・ジャイロ（rotation_vectorも無し）

活用候補：水平器（加速度で車体の傾き、固定マウント前提）・車内カメラの定期撮影・停車中の揺れ検知（防犯）・騒音レベル記録。

④ 音声操作（ウェイクワード「ハイエース」）設計合意・未着手

例:「ハイエース！」→「現在のSOCの%を教えて」→「現在、85%です」
決定事項（2026-10-10）:
・Pi5で聞いてPi5が答える（USBスピーカーフォンを1台追加。タブレットが寝ていても動く）
・聞く＋安全な操作（SOC・電圧・車内温度・CO2・天気・通信量／照明・ファン・エアコンIR・プロジェクター）。充電停止・BMSスイッチ等の電源系は声では操作しない
・認識は普段オフライン、分からなければAI：ウェイクワードと決まった言い回しはVosk（無料・オフライン）、読み上げはOpen JTalk、それ以外の質問はClaude APIへ（オンライン時のみ、要APIキー）
タブレット単体を採用しなかった理由: Termuxからはマイクを連続で受け取れず（数秒ずつ録音→送信になり聞き逃し・遅延）、ブラウザの音声認識は画面オン・前面表示が必要、Android標準のウェイクワードは変更不可。
Pi5の現状: マイク・スピーカーなし（HDMI音声のみ）、メモリ空き6.9GB/8GBで余裕あり。
スピーカーフォンの条件: USB接続だけで使える（UAC対応・ドライバー不要）、エコーキャンセル付き、全方向マイク。
次の手順（一時停止中）: 1. Pi5にVosk・Open JTalkを導入し、読み上げ音声で作った録音で認識テスト → 2. 質問・操作の対応づけ（文字入力でテスト）→ 3. AIへの回送（APIキー準備）→ 4. スピーカーフォン到着後に車内で誤反応・自声の拾い込みを調整
